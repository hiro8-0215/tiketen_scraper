## 結論

GitHubの実コミットを複数日チェックアウトして比較した結果、現在のmasterは正常な
最新データではありません。2026-07-28 01:31の収集で、直前までlistingだった3,795件の
うち3,791件が一度にdeletedへ変更されています。市場全体が短時間に終了したのではなく、
取得失敗・不完全レスポンスを「掲載消失」と解釈した収集処理の障害です。

`tiketen_date_data/data_8_26`の14個の通常masterは、ローカル`github_now`のmasterと
SHA-256で一致しています。フォルダ名は8月26日ですが、最終観測は7月28日です。

## 原因

旧スクレイパーには次の組合せがありました。

1. HTML/API例外を空データまたは途中データとして処理する
2. 取得に成功したイベントと失敗したイベントを区別しない
3. 今回のactive集合にいない過去listingを全件deletedにする
4. 一度誤ってdeletedにした行がAPIでactiveに戻ってもlistingへ復元しない
5. deleted後にsold応答を確認してもsoldへ更新しない
6. sold照合がイベントIDを含まず、同時刻・同価格で衝突し得る

GitHub Actionsは`workflow_dispatch`のみで、リポジトリ内に定期scheduleはありません。
履歴も7月28日で終了しており、`data_8_26`は8月26日収集分ではありません。

## 実施した防止策

- 通信・JSON・pagination・イベントID異常をfail-closed化
- 完全に検証できたイベントだけ掲載消失を反映
- 将来公演でactiveが全消失、または80%超が説明なく消失した応答を拒否
- 明示的なactive応答で誤deletedをlistingへ復元
- 明示的なsold応答でdeletedを含む非sold状態をsoldへ更新
- sold照合キーと生成IDへイベントID・価格を含めて衝突を防止
- 学習一括ランナーの先頭にsnapshot品質ゲートを追加
- 複数masterで同一ID・同一時刻のstatusが競合した場合は、soldをdeletedより優先して
  決定的に重複排除

## 再構築への影響

- **Model 16適正価格**: sold行だけを学習するため、誤deleted行が直接教師値に混ざる
  わけではありません。ただしdeleted後の本当のsoldが拾えず、sold母集団が欠落して
  います。現モデルは暫定基準として残せますが、論文・最終評価用にはクリーン期間を
  蓄積後に再学習・再評価します。
- **需要状態モデル**: deleted教師が破損しているため再学習必須です。既存の精度は
  実需要ではなく収集障害を予測している可能性があります。
- **安価な代替出品モデル**: 誤った終了時刻で観測窓とラベルが切られるため再学習必須です。
- **買い時モデル**: 上記2モデルを入力にするため再学習必須です。
- **LLM意味特徴**: 価格・結果を教師にしない説明文キャッシュは再利用できます。新規説明文
  だけ差分抽出します。

欠測期間に「実際にいつ売れた／消えたか」は復元できません。7月28日に一括deletedと
された3,791件を推測で修正せず、未確定・打切りとして除外するか、修正後の新規観測から
クリーンな期間を作る必要があります。
