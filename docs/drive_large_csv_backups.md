# Google Driveの大きなmaster CSVへの対応（2026-10-10）

## 障害の原因

`Daily Archive to Google Drive`は、`snow-man_master.csv`が約37 MiBとなり、
アップローダーの35 MiB上限で停止しました。収集ワークフローは成功しています。
2026-10-10の実行例: [失敗ログの実行](https://github.com/hiro8-0215/tiketen_scraper/actions/runs/38027739974)。
JSONLや通信の一時障害とは別の原因で、再試行だけでは解消できません。

## 変更するもの・互換性

- GitHubの`data/*_master.csv`の名前、CSV列、値、レコード順は変更しません。
- Driveへの送信時に、35 MiBを超えるmasterだけを1ファイル30 MiB以下へ分割します。
  例: `snow-man.part001_master.csv`、`snow-man.part002_master.csv`。
- 各partは元のヘッダーを持つCSVです。引用符内の改行を含む説明文も途中で切りません。
- 毎回`drive_backup_manifest_master.csv`を保存します。全masterの元ファイル名、
  サイズ、レコード数、SHA-256と、使用するpartの順序・サイズ・SHA-256を記録します。
  分割不要のmasterは元の名前のまま保存し、この一覧にも記録します。
- partも検証用CSVも既存Apps Scriptの`*_master.csv`許可規則に適合します。
  **この修正のためのApps Script再デプロイやSecret変更は不要**です。
- JSONL保存の有効化・再デプロイ要件は従来どおりです。

**Driveの日付フォルダをそのまま学習・集計の入力にしないでください。**
既存モデルは`*_master.csv`からアーティスト名を決めるため、part名を直接渡すと
アーティストIDが変わり、検証用CSVも入力に混入します。下の復元コマンドで
元の名前に戻したフォルダを、従来のsnapshotフォルダとして使用してください。
GitHubの`data/`を直接使う処理にはこの復元は不要です。

## Driveからダウンロードしたデータの復元

1. Actionsのアーカイブ実行が成功した後、Driveの日付フォルダを丸ごとダウンロードし、
   ZIPを展開します。検証用CSVと、そこに記載された全master/partが必要です。
   出力には空のフォルダ、または同じsnapshotの復元先を指定してください。
2. リポジトリ直下で実行します。入力と出力は別のフォルダを指定してください。

```powershell
python restore_drive_backups.py --source-dir "C:\backups\data_10_10" --output-dir "C:\snapshots\data_10_10"
```

3. 出力側には`*_master.csv`が元のアーティスト名で生成されます。このフォルダを
   既存モデルのsnapshot入力に指定します。検証用CSVやpartは出力しません。

復元では全ファイルのヘッダー、part順序、サイズ、レコード数、SHA-256を検証します。
復元後はBOM、引用符、改行形式も含めて**元CSVとバイト単位で一致**します。
検証が全masterで完了するまでは出力先の既存CSVを置き換えません。ファイル不足や
新旧part混在、破損があればエラーで停止し、再ダウンロードが必要です。
旧形式の分割のない日付フォルダも同じコマンドでコピーできます。

## 保存の順序と運用上の限界

- 送信前に全ファイルを確認して必要な分割を一時フォルダへ作成します。元CSVは編集せず、
  一時ファイルは成功・失敗にかかわらず削除します。
- データを送信し、全件成功後に検証用CSVを最後に送信します。データが失敗した場合は
  新しい検証用CSVを公開せず、Actionsも失敗します。既存の再試行・全体15分予算を共有します。
- 同じ日には固定part名を上書きします。毎時別名の大型ファイルを蓄積しません。
  古い余剰partや、分割前の同名masterがDriveに残る場合があります。
  復元では最新の検証用CSVにあるファイルだけを使い、これらは無視します。
  CSVが小さくなった場合も一覧を更新するので、古いpartを復元することはありません。
- Driveの日付フォルダ全体の更新はトランザクションではありません。送信失敗中・
  送信途中に取得すると検証に失敗する場合があります。成功した実行後に取得してください。
- 1レコードだけでヘッダー込み30 MiBを超える場合は安全に分割できず、明示的に失敗します。
  Drive容量、Apps Script実行・転送制限、通信障害もこの変更では無制限にはなりません。

## 検証

自動テストでは、複数行の日本語説明、BOM、CRLF、終端改行なしの完全復元、
破損・欠損・順序不正・パス不正の拒否、新旧ファイルの混在検知、元CSVの非変更、
part送信失敗時に検証用CSVを送らないこと、送信時間予算の共有を確認します。
実データについても分割・復元後のSHA-256一致を確認します。

今回のローカル検証は104テスト成功。`af1b5fcd`の実データ13 master CSVを
14データファイル＋検証用CSVへ変換し、全13 masterの復元後SHA-256が一致しました。
Snow Manの元サイズは38,811,356 bytes、partは31,457,194 bytesと7,354,746 bytesです。
元CSVと復元CSVのSHA-256:
`b9ae0aeb35bd2fac306ec6fa6427838733e11bed7006568d945439afcd7f43e9`。
