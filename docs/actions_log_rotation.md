# 変更履歴ログの分割とGitHub Actions復旧

## 障害の原因と影響

2026-09-30 20:00（日本時間）開始の`Ticket Scraper`で、日次ログ
`data/ticket_changes_20260930.jsonl`が100.42 MBになり、GitHubの1ファイル100 MB制限に
よりpushが拒否されました。直前の19:00開始の実行では99.89 MBで保存できていました。
2026-10-01 03:00開始の実行では102.88 MBまで増えています。

- 最初の失敗: https://github.com/hiro8-0215/tiketen_scraper/actions/runs/36705896881
- 最新の調査対象: https://github.com/hiro8-0215/tiketen_scraper/actions/runs/36755495762

テスト、API収集、公開チケット詳細取得は成功しています。データのcommit後のpushで
失敗したため、失敗した実行の更新はGitHubへ反映されませんでした。後続の品質確認も
スキップされ、収集ワークフローの成功を条件とするGoogle Driveバックアップも停止しました。
失敗したランナーだけに存在した観測履歴は、保存済みデータから復元できるとは限りません。

変更前は、価格・状態・本文などの変更前後のレコードを、日付ごとに1つのJSONLへ
無制限に追記していました。日付が切り替わると一時復旧する可能性がありますが、
同じサイズ上限への再到達を防ぐ必要があります。

## 変わるもの・互換性

- 新しい名前は`ticket_changes_YYYYMMDD_001.jsonl`、`_002.jsonl`…です。
  999を超える場合も連番を継続します。日付は従来どおり実行環境のローカル日付で、
  GitHubのUbuntuランナーではUTCです。日本時間の深夜にも前日のUTCログへ追記します。
- 最大サイズは30 MiB（31,457,280 bytes）です。GitHubの100 MB制限と
  Driveアップローダーの35 MiB制限の両方に余裕を確保します。
- JSONLの1行を分割せず、レコードを書き込む前に次のファイルへ切り替えます。
  `ticket_change_v1`のキー、値、変更前後の全文、日時、レコード順を維持します。
  `*_master.csv`の列や値は変更しません。履歴の間引きや削除はしません。
- 旧名`ticket_changes_YYYYMMDD.jsonl`も読み込めます。読者は1日1ファイルの固定名ではなく
  `ticket_change_log.change_log_paths(folder)`を使用します。日付と数値の連番順で返ります。
  `ticket_changes_*.jsonl`のglobも両形式に一致します。
- 収集結果の監査とDriveアップローダーは上記の読み込み関数に対応しています。
  外部の学習コードで日付だけの固定ファイル名を指定している場合も、全partを読むよう
  修正してください。レコードの解釈は従来と同じです。

## 既存ログの移行と安全対策

```bash
python ticket_change_log.py --data-dir data
```

旧名のログを行境界で分割し、一時ファイルへ保存します。分割ファイルを連結した
SHA-256が元ファイルと一致し、元ファイル自体も処理中に変わっていないことを確認します。
全partの公開と再検証が成功してから旧ファイルを取り除きます。記録内容は再シリアライズ
しないため、Unicodeの表現や改行を含めて元のバイト列を維持します。
標準出力には元名、part数、行数、SHA-256、検証結果を出します。

途中で停止した場合は同じコマンドを再実行できます。既に公開されたpartの内容が
一致する場合は再利用し、異なる場合は元ファイルを残して停止します。単一レコードが
30 MiBを超える、末尾行が途中で切れている、または番号付きpartが上限を超える場合も
処理を止めて異常を通知します。元ファイルを失うような自動切り捨ては行いません。
一時ファイルは処理後に片付けます。

GitHub Actionsは、回帰テスト後、収集前に移行コマンドを実行します。
ローカルから直接収集した場合も当日の旧ログは追記前に移行します。
書き込みは従来どおり単一プロセスを前提とし、Actionsの`ticket-scraper`排他制御を継続します。

## GitHubとGoogle Driveへの反映

1. 分割済みの既存ログとコードの修正を同じ変更で`main`へ反映します。
   削除した旧ファイルの履歴をGitから消す必要はありません。番号付きpartは全て30 MiB以下です。
2. `Ticket Scraper`を実行し、収集・push・品質確認の成功を確認します。
   手動再実行では修正後の`main`をcheckoutします。
3. master CSVのみのDriveバックアップは従来の設定で動きます。
   JSONLも保存する場合は、更新した`google_drive_apps_script/Code.gs`をApps Scriptへ貼り付け、
   「デプロイを管理」から新しいバージョンへ再デプロイします。新しいファイル名を受け付ける
   コードの反映後に、GitHub Actions変数`GDRIVE_INCLUDE_JSONL=true`を有効にしてください。
   すでにtrueの場合は、次のバックアップ実行前に再デプロイしてください。
4. `Daily Archive to Google Drive`を実行し、masterと、有効化した場合は全partが保存される
   ことを確認します。旧名のDriveファイルが過去のバックアップに残る場合は、旧名とpartを
   同時に読み込んで二重集計しないよう、GitHub側の移行済みファイル集合を使ってください。

今回の移行で保証するのは保存済み変更履歴の完全保持です。失敗した実行の過去の観測を
後から作成したり、現在の状態を過去の観測として埋めたりはしません。

## 確認方法

```bash
python -m unittest discover -s tests -q
```

サイズ境界、複数回の追記、日付切り替え、Unicodeと改行を含む移行のバイト一致、
途中停止からの再開、競合時の元データ保持、番号順の読み込み、Driveへの全part送信を
回帰テストで確認します。既存ログの移行時にも実データのSHA-256一致を確認します。
