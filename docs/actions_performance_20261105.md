# Actionsの速度と保存失敗の修正（2026-11-05）

## 原因と実測

[失敗実行41843343248](https://github.com/hiro8-0215/tiketen_scraper/actions/runs/41843343248)
（11月4日23時開始、日本時間）の内訳です。

| 処理 | 実測時間 |
| --- | ---: |
| Gitチェックアウト | 12分48秒 |
| 依存関係・テスト等 | 23秒 |
| API状態の取得・消えたshareCodeの確認 | 23分9秒 |
| 公開全文の再取得 | 24分4秒 |
| コミット・push（失敗） | 1分19秒 |

直接の失敗原因は時間切れではなく、**更新後の`data/snow-man_master.csv`が101.08 MiBと
なり、GitHubの100 MiB制限でpushを拒否された**ことです。最後の成功時は99.11 MiBで、
以降は同じ古いmasterからshareCodeの回転を再確認し続けています。Driveも収集失敗により
スキップされます。調査時HEAD `baee9a49`の`data/`は約14.327 GB、13 master合計は約291 MBです。

## 変更と互換性

### チェックアウト

収集は`fetch-depth: 1`と非coneのsparse checkoutを使用し、全Git履歴、過去の変更履歴、
再生成可能な月次snapshotのblobを取得しません。現在master・targets・匿名売却在庫・
監査用観測履歴・UTC当日/翌日の変更履歴を取得します。`git add --sparse data/`で更新し、
取得していない過去ログもGitのツリーに保持します。履歴削除・force pushはしません。
Driveはmasterとコードだけを取得し、JSONLを明示的に有効にした場合だけJSONLを追加取得
します。その場合の転送量は大きいままです。定期処理はHTTP問い合わせで動くためChromium
のインストールも省きます。手動ブラウザ収集時は`playwright install chromium`が必要です。

### CSVのGit保存形式

`repository_data_storage.py`は50 MiB以上のCSVを`.csv.gz`へ可逆圧縮します。
一度圧縮したファイルは小さくなっても同じgzip形式を維持します。
圧縮前後のSHA-256一致と、処理中の元CSVの不変を検証してから置き換えます。
**列・値・レコード順・全文・履歴を削りません。** 初回は大きなmasterと月次snapshotを移行します。

Git上では例として`snow-man_master.csv`が`snow-man_master.csv.gz`になります。
直接CSVのraw URLを参照する外部処理には変更が必要です。Actionsは開始時に元名CSVへ
自動展開します。Driveも従来のCSVを送信し、part分割・復元ツールの仕様は維持します。
ローカル分析・学習の前にも次を実行してください。

```powershell
python repository_data_storage.py restore --data-dir data
```

編集済みCSVとgzipの内容が違う場合は上書きせずエラーになります。CSVを退避してから
復元してください。復元CSVは未追跡に見えます。**手動コミットでも先にpackしてください。**
packはCSVをgzipへ戻すので、分析終了後に実行します。

```powershell
python repository_data_storage.py pack --data-dir data
git add --sparse data/
```

圧縮後も95 MiB以上の場合は元CSVを残して明示的に失敗します。蓄積量が無制限に増えても
対応できるものではなく、長期的には履歴の別ストレージへの移管が必要です。

### 同じ実行内の公開レスポンスの再利用

消えた古いshareCodeの確認で新しいcanonicalコードとイベントを検証できた場合、
同じ応答を新コードでも参照可能にします。実行専用一時ファイルでAPIフェーズから全文
フェーズへ引き継ぎ、同じ問い合わせを省きます。API観測/状態確認以上に新しい、
コードとイベントが一致した応答だけが対象です。古い応答、null、取得失敗、不正イベント、
他の毎時実行の応答は再利用しません。全アクティブ行と全文の品質監査を維持します。
同時問い合わせ数2と取得後0.5秒待機を維持し、サイトへの並列負荷は増やしません。
ログの`[PUBLIC CONTENT CACHE]`で再利用件数を表示し、出力をバッファリングしません。
全文取得後の重複したmaster全体の書き出しも省きます。

### 品質と進捗の保存

圧縮前に監査します。品質が不完全でも進捗はGitへ保存し、保存後にワークフローを失敗に
します。品質不足を成功扱いしたり、Driveへ成功通知したりしません。次回は保存済み状態から継続します。

## 検証・制約

単体テストと一時Gitリポジトリで、sparse更新時の過去ログ保持、複数行日本語・BOM・CRLF・
末尾改行なしの完全復元、gzip破損時と編集済みCSVの保護、応答再利用と古い応答の再取得、
イベント不一致の拒否を確認します。実データ移行はWindowsの改行変換を避け、元Git blobの
SHA-256とgzip展開後のSHA-256を照合します。

本番の短縮時間は次回Actionsのstep時間と再利用件数で確認します。出品数・shareCode回転数・
通信遅延で変動するため、ローカル試験だけで所要時間は断定しません。外部の毎時トリガー、
40分の内部上限、90分のジョブ上限は維持します。

初回移行・ローカル検証の結果:

| 対象 | 元Git blob (bytes) | gzip (bytes) |
| --- | ---: | ---: |
| Snow Man master | 103,925,273 | 14,803,976 |
| なにわ男子 master | 59,992,958 | 8,934,373 |
| Snow Man 2026-10 snapshot | 84,286,931 | 12,050,259 |
| なにわ男子 2026-10 snapshot | 52,652,990 | 7,861,702 |

4ファイルとも元Git blobとgzip展開後のSHA-256が一致しました。115件のテストと
actionlintによる2ワークフロー検査が成功。実データ13 masterをGit gzipから展開し、
Drive用18データファイル＋検証用CSVへ変換・復元して、全masterのSHA-256一致も確認しています。
