# 2026-10-06 Actionsの一時障害と復旧対応

## 2026-11-14追記: Driveの時間上限

[11月13日の失敗](https://github.com/hiro8-0215/tiketen_scraper/actions/runs/43346059992)では、
個別ファイルの通信タイムアウトと再試行が重なり、送信全体の15分を使い切りました。
直近の成功例でも約10〜14分かかっているため、送信・再試行の上限を15分から25分へ、
準備を含むDriveジョブ全体の上限を20分から30分へ延長します。
送信対象、ファイル形式、同時実行の制御は維持します。
データと検証用CSVは同じ25分を共有し、すべての送信が成功した時点で終了します。

## 2026-11-16追記: 収集の連続失敗と復旧手順

[9時台のActionsログ](https://github.com/hiro8-0215/tiketen_scraper/actions/runs/43777845214/job/133008109764)
では、個別出品の詳細APIで1,209件のHTTPエラーがあり、40分の上限までに全文更新が完了しませんでした。
GitHubにデータは保存できましたが、詳細が古い出品が残ったため品質判定で失敗し、Drive保存は開始されませんでした。
旧ログにはHTTPステータス番号がなく、当時の応答原因は断定できません。

- 詳細APIのHTTPステータスと件数を記録します。401/403/404は同じ出品で直ちに繰り返さず、
  401/403が連続するとその取得工程の新規リクエストを保留します。429と `Retry-After` が付いた503は、
  2つのワーカーと同じ実行の次の取得工程で待機を共有します。一時エラーの再試行は残り時間内に限ります。
- 詳細に到達しなかったグループを次回の先頭へ回します。取得失敗・保留の場合は最後に確認済みの詳細を残し、
  今回確認したという印は付けません。公開詳細で確認した旧IDの連鎖は、同一公演内だけで最終IDに整理し、
  過去の行は残します。
- 空の公演一覧は「全件」と「販売中のみ」の両方が空の場合に確認済みと記録します。既存出品を
  売却・削除と推定せず、個別結果で確認できるまで保留します。両方が一致しない場合や公演取得に失敗した場合は、
  回収済みデータをGitHubへ保存してから失敗を報告します。
- 一過性のGitHub push拒否（`commit_refs_rules`、一部のゲートウェイエラーなど）だけ再試行します。
  毎回最新の `main` を取り込み、認証・サイズ制限・競合を強制pushで回避しません。
- Driveは初回に各ファイル最大2回まで送信し、送れないファイルは他を先に保存してから再試行します。
  送信と検証用CSVは25分の共通上限、ジョブ全体は30分です。収集品質が未確認の版で、直前の正常な
  Driveバックアップを上書きすることはありません。品質が通れば従来どおり自動保存します。

反映後は `PUBLIC CONTENT HTTP SUMMARY`、`COLLECTION COVERAGE`、品質監査の `error_counts`、
GitHubへの保存、連続したDrive保存の完了を確認します。サービス側が拒否を続ける場合は未確認として扱い、
取得済みと見なして成功させません。

## 確認した原因

直近100実行（収集50回とバックアップ50回）では、それぞれ1回の失敗を確認しました。

1. 収集: 2026-10-06 05:00（日本時間）開始の
   [実行37367069889](https://github.com/hiro8-0215/tiketen_scraper/actions/runs/37367069889)は、
   `The job was not acquired by Runner of type hosted even after multiple attempts`
   というGitHubの失敗注釈で終了しました。runner_idは0、実行ステップは0件で、
   スクレイパーは起動していません。コードからGitHubのホストランナー不足を解消することは
   できないため、最新mainから再実行して復旧を検証します。ランナー起動前の失敗は
   ワークフロー内の再試行処理でも救済できません。
2. Drive: 2026-10-06 03:27（日本時間）開始の
   [実行37356114734](https://github.com/hiro8-0215/tiketen_scraper/actions/runs/37356114734)で、
   `ae-group_master.csv`の送信がHTTP 404およびJSONではない応答により5回失敗しました。
   最初のファイルは送信でき、次の通常バックアップは成功しています。恒久的な認証エラー
   より一時的なApps Script/Google側の応答障害を示す状況です。

前回対策した100 MB制限によるpush拒否は、この調査範囲では再発していません。

## 修正内容とデータへの影響

- 1ファイル内の再試行間隔を1/2/4/8秒から10/20/40/60秒へ延長します。
- HTTP 404、408、429、5xx、通信タイムアウト、JSONとして解釈できない応答などの
  一時エラーが5回続いた場合は、そのファイルを保留して他のファイルを保存します。
  60秒後と120秒後に、失敗したファイルのみを最大2回の追加パスで再試行します。
- 保存済みのファイルを追加パスで再送しません。全ファイルの保存に成功したときだけ
  `Google Drive backup completed.`を出し、未保存ファイルが残れば失敗を報告します。
- 全体に15分の時間予算を設け、待ち時間と通信タイムアウトを残り時間で制限します。
  バックアップジョブの20分上限を維持します。
- 401/403、ファイル容量超過、Apps Scriptの明示的な拒否などは追加パスへ回さず、
  対処が必要なエラーとして終了します。
- CSVの列・値、JSONLの形、ファイル名、保存先フォルダは変更しません。
  GitHub SecretsやApps Scriptの再デプロイは今回のクライアント側修正に不要です。

一時障害を必ず解消できる保証はありません。15分の時間予算を超えてサービスが
復旧しない場合は、成功したファイルを保存した状態でジョブを失敗にし、再実行を促します。
収集の成功とDriveバックアップの成功は別々に確認してください。

## 検証

```bash
python -m unittest discover -s tests -q
```

一時エラーの分類、失敗したファイルのみの再試行、永続エラーの即時終了、保存に失敗した
状態で成功を報告しないこと、時間予算と通信タイムアウトを回帰テストで確認します。
push後はGitHub上で収集とDrive保存を実行し、各ステップと全ファイルの保存結果を確認します。
